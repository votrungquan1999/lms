# lms

## Writing tests and exams

- **Show data as code, never in a sentence:** `scores = [30, 20, 10]` (C++: `vector<int> scores = {30, 20, 10};`), records as tuples or pairs, file contents in a labelled block. Students can't be assumed to read "holds 30, 20, 10" as an array.
- **Print every program a question names** ("the slow program", "the binary search from the lesson"); for big inputs print the program and state only the file sizes. No questions about program structure (comparing whole programs); use short trace questions ("what does this print?").
- **Never hand over a number that answers the question, and no obvious bugs or contest trivia.** Good traces need the mechanics: where lo and hi end after a miss, why `lo = mid` never stops, how `while lo < hi` misses the last number.
- **No redundant add-ons in coding tasks, harder multiple-choice later in Part A, and no cross-question leaks:** a multiple-choice question must not print a coding question's solution or reuse its example data, and a coding example must not show a multiple-choice answer.
- **Before seeding a test:** scan every multiple-choice question for "holds", "has … already read into", "were read into" and questions with no code block; run each snippet as written in Python and C++; and have an independent reviewer sub-agent check every question against these rules. Update a live question through `QuestionService.updateQuestion` with the existing option ids, which writes the change log.
- **Exam limits:** before changing a classic problem's limits, look up the classic version (SPOJ, UVa, POJ, Codeforces) and what it tests, and cap input values rather than something students can't control. Never state a step count or run time you haven't measured: build a worst-case file for every Part B program, time the student's exact Python program on it with a timeout, and leave headroom for school PCs 2-4x slower.
- **Practice formats the owner picked:** tracing as multiple choice (which lo/hi/mid sequence is right), speed as step-count multiple choice ("1,000,000 steps per second; how long on this input?"), find-the-bug, faded steps for new ideas (full program, then blanks, then a blank page), and many rewrites of binary search and prime code plus nested-loop drills. No hand-written traces, timing experiments or explaining at the board, and no planning around AI use, unless he asks.

## Seeding and real-AI runs

- **Seed tests from a temporary worktree of `origin/main`**, not the local checkout, which lags main: copy in `.env.local` and the data file, run `npx tsx --env-file=.env.local scripts/create-test.ts <data file>`, then remove the worktree. Don't use bun (it crashes on the lockfile's `bson`). `.env.local` points at the live Atlas database, so run the seed exactly once, then read the test back.
- **`pnpm test:e2e:real-ai` is a demo, not a test.** It shows the owner how AI question import behaves on a real exam, so use real services where he will look (real S3 with the local-dev access key kept in personal-infra) and report what it did, not pass/fail. Browser uploads from localhost:3005 hit the bucket's CORS list (only localhost:3000 is allowed); relay the PUT through Playwright instead of changing infra.
- **Gemini free tier allows 20 requests a day** for gemini-3.5-flash, shared by production grading/import and e2e runs, and 503 "high demand" replies count (the AI SDK makes up to 3 attempts per call). Never poll Gemini to wait out overload; prefer `GEMINI_MODEL_ID=gemini-2.5-flash` for test runs and check the quota before repeated calls. The quota resets at midnight Pacific.
